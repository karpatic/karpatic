FreeCAD / SpaceMouse Setup Record

Active state:

  • spacenavd running in user mode.
  • Socket: ~/run/spnav.sock.
  • FreeCAD: /usr/bin/freecad from APT.
  • Linked against system libspnav.
  • Snap/AppImage removed.

Reinstall the working repository build:

sudo apt update
sudo apt install freecad

Verify the APT binary:

which freecad

Expected:

/usr/bin/freecad

Ensure spacenavd is running in user mode:

pgrep -a spacenavd
ls -l ~/run/spnav.sock

If it is not running:

mkdir -p ~/run
spacenavd -d &
disown

Launch FreeCAD using the socket:

SPNAV_SOCKET=$HOME/run/spnav.sock freecad

If SpaceMouse works, make it permanent by adding this to ~/.profile, then log out and back in:

export SPNAV_SOCKET=$HOME/run/spnav.sock

Result:

  • System FreeCAD from APT.
  • User-mode spacenavd.
  • No Snap version interfering.

Packaging Difference

SourceBinary pathLinked to libspnav?SpaceMouse
Snap 1.0.2/snap/bin/freecadNoNo
AppImage 1.0.2 (conda)standalone bundleNoNo
APT 0.20.2/usr/bin/freecadYesYes

Why Snap/AppImage failed:

  • Snap sandbox isolation blocks access to /dev/input/event* and custom Unix sockets such as ~/run/spnav.sock.
  • The spacenavd socket was invisible to Snap, so there was no daemon connection.
  • The conda AppImage build used bundled libraries and did not include or link libspnav.
  • Grepping inside the AppImage showed no spnav symbols, so FreeCAD never attempted to connect.

Why APT worked:

  • It is compiled against system libspnav.
  • It respects SPNAV_SOCKET.
  • It can talk to user-mode spacenavd.
  • It has no sandbox isolation.

Root cause:

FreeCAD -> libspnav -> spacenavd -> /dev/input/eventX

Snap/AppImage broke that chain; APT preserved it.

For FreeCAD 1.0.x with SpaceMouse support, use a non-Snap, non-conda build compiled with libspnav enabled, installed from source or a proper PPA.

Node Worker Threads

Node.js worker threads are problematic, but they work great for us:

  • https://www.inngest.com/blog/node-worker-threads
  • Good writeup on event-loop starvation.
  • Isolating critical websocket / heartbeat work from CPU-heavy user code can be useful.
  • worker_threads tradeoffs include a separate file entrypoint, structured-clone message passing, bundler detection issues, and non-trivial memory/startup overhead.
  • Practical pattern: keep connection internals in a long-lived worker thread, run user code on the main thread, use protocol messages, and respawn with exponential backoff.

JavaScript Bloat

The Three Pillars of JavaScript Bloat:

  • https://43081j.com/2026/03/three-pillars-of-javascript-bloat
  • Useful framing for npm dependency bloat.
  • Pillar 1: old-runtime, cross-realm, and primordial-safety compatibility code most apps do not need.
  • Pillar 2: "atomic" micro-packages that should often just be inlined.
  • Pillar 3: ponyfills that stayed long after native support landed.
  • Good reminder to ask why a dependency exists, prefer native platform features, and use tools such as knip, e18e, and npmgraph to audit dependency trees.
